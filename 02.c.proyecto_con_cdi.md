# 💉 Proyecto de Práctica — Con CDI

> ⚠️ **Nota:** Este proyecto es la transformación del proyecto `01-web-app-without-cdi`.
> Partimos del mismo código base y lo refactorizamos progresivamente para usar **CDI
> (Contexts and Dependency Injection)** de Jakarta EE, eliminando la creación manual
> de objetos y reemplazándola por inyección de dependencias con anotaciones.
>
> Los cambios son **internos** — visualmente la aplicación se comporta exactamente
> igual que antes. Lo que cambia es la forma en que los objetos se crean, se
> relacionan y se gestionan: de instanciación manual a un contenedor CDI que
> lo hace por nosotros.
>
> Este proyecto sigue la guía del curso
> [Andrés Guzmán / Sección 56: Jakarta EE9: CDI - Inyección de dependencias y contextos.](https://www.udemy.com/course/master-completo-java-de-cero-a-experto/learn/lecture/27405210#overview)

## 🔄 ¿Qué cambia respecto al proyecto sin CDI?

| Aspecto                     | Sin CDI                               | Con CDI                                     |
|-----------------------------|---------------------------------------|---------------------------------------------|
| **Creación de objetos**     | `new ProductServiceImpl(connection)`  | `@Inject ProductService productService`     |
| **Gestión de dependencias** | Manual — cada clase crea las suyas    | El contenedor CDI las resuelve              |
| **Ciclo de vida**           | Manual — el desarrollador lo controla | Gestionado por el contenedor según el scope |
| **Acoplamiento**            | Alto — clases concretas entre sí      | Bajo — interfaces + inyección               |
| **Conexión a BD**           | Se pasa manualmente por constructor   | Se inyecta via `@Produces`                  |

## ⚙️ Configurando el proyecto para CDI

En el `pom.xml` agregaremos las siguientes dependencias para habilitar CDI:

### Agregando la dependencia `jakarta.inject-api`

Desde el inicio del proyecto hemos trabajado con `jakarta.jakartaee-api` con `scope=provided`, lo que significa que esa
dependencia **no viaja dentro del `.war`** — asumimos que el contenedor (Tomcat) la proveerá en runtime.

Esto funciona bien para **Servlet y JSP** porque Tomcat sí los incluye. Sin embargo, cuando comenzamos a usar CDI
necesitamos clases como `jakarta.inject.Provider` que Tomcat **no provee** — y al tenerlas como `provided` tampoco
viajan en el `.war`, causando un error al arrancar:

```
java.lang.NoClassDefFoundError: jakarta/inject/Provider
java.lang.ClassNotFoundException: jakarta.inject.Provider
```

La solución **no** es quitar el `scope=provided` de `jakarta.jakartaee-api`, porque eso incluiría toda la API de Jakarta
EE en el `.war` generando:

- `.war` innecesariamente pesado (~10MB extra)
- Clases duplicadas con las que Tomcat ya provee (Servlet, JSP)
- Posibles conflictos de versiones en runtime

La solución correcta es agregar **únicamente** lo que Tomcat no provee y necesitamos — la API de inyección de
dependencias:

```xml

<dependencies>
    <!-- Especificación Jakarta EE completa — scope provided porque Tomcat
         provee Servlet/JSP. No viaja en el .war -->
    <dependency>
        <groupId>jakarta.platform</groupId>
        <artifactId>jakarta.jakartaee-api</artifactId>
        <version>11.0.0</version>
        <scope>provided</scope>
    </dependency>

    <!-- API de inyección de dependencias — SIN scope provided porque Tomcat
         NO la provee. Debe viajar en el .war para que Weld funcione en runtime -->
    <dependency>
        <groupId>jakarta.inject</groupId>
        <artifactId>jakarta.inject-api</artifactId>
        <version>2.0.1</version>
    </dependency>
</dependencies>
```

En resumen, el criterio para decidir si una dependencia lleva `scope=provided`
o no cuando usamos Tomcat es claro:

| Dependencia             | `scope=provided` | ¿Por qué?                                             |
|-------------------------|------------------|-------------------------------------------------------|
| `jakarta.jakartaee-api` | ✅ Sí            | Tomcat provee Servlet/JSP en runtime                  |
| `jakarta.inject-api`    | ❌ No            | Tomcat no provee inyección CDI — debe ir en el `.war` |
| `weld-servlet-core`     | ❌ No            | Es la implementación CDI — debe ir en el `.war`       |

### Agregando la dependencia `Weld`

```xml

<dependency>
    <groupId>org.jboss.weld.servlet</groupId>
    <artifactId>weld-servlet-core</artifactId>
    <version>6.0.4.Final</version>
</dependency>
```

#### ¿Por qué necesitamos esta dependencia?

CDI es una **especificación** — define el contrato: las anotaciones (`@Inject`, `@ApplicationScoped`, `@Produces`...),
las interfaces y las reglas. Estas anotaciones ya están disponibles en nuestra dependencia `jakarta.jakartaee-api`, por
lo que el compilador no se quejará si las usas. Sin embargo, **tenerlas disponibles no significa que funcionen** — la
especificación solo define el "qué", no el "cómo".

Para que `@Inject` realmente inyecte algo en runtime, para que `@ApplicationScoped` realmente cree una sola instancia,
para que `@Produces` realmente registre un bean — necesitamos una **implementación** que ejecute toda esa lógica. Ahí es
donde entra `Weld`:

```
jakarta.jakartaee-api  →  especificación CDI  →  define @Inject, @ApplicationScoped, @Produces...
                                                  ⚠️ Las anotaciones existen pero no funcionan solas

weld-servlet-core      →  implementación Weld →  hace que @Inject realmente inyecte en runtime
                                                  hace que @ApplicationScoped realmente sea singleton
                                                  hace que @Produces realmente registre el bean
```

Es el mismo patrón que encontramos en todo Jakarta EE:

| Especificación                            | Implementación                 |
|-------------------------------------------|--------------------------------|
| **Jakarta CDI** (`jakarta.jakartaee-api`) | **Weld** (`weld-servlet-core`) |
| Jakarta JPA                               | Hibernate                      |
| Jakarta Servlet                           | Tomcat                         |
| JSTL API                                  | GlassFish JSTL                 |

#### ¿Por qué necesitamos agregarlo manualmente en Tomcat?

En servidores de aplicaciones completos como **WildFly, Payara o GlassFish**, Weld ya viene incluido — no necesitas
agregar nada porque el servidor ya trae tanto la especificación como su implementación.

Pero **Tomcat es solo un contenedor web** (Servlet Container), no un servidor de aplicaciones completo, por lo que no
incluye la implementación CDI de forma nativa:

```
Servidor completo (WildFly, Payara...)
    ├── jakarta.jakartaee-api  →  especificación CDI ✅  (ya viene incluido)
    └── Weld                   →  implementación CDI ✅  (ya viene incluido)

Tomcat (solo contenedor web)
    ├── jakarta.jakartaee-api  →  especificación CDI ✅  (incluida en el .war al compilar)
    └── Weld                   →  implementación CDI ❌  (necesitamos agregarlo manualmente)
```

> 📌 **Nota sobre `scope=provided` y `Tomcat`:** Nuestra dependencia `jakarta.jakartaee-api` tiene `scope=provided`,
> lo que normalmente significa que el contenedor la proveerá en runtime. Sin embargo, `Tomcat` no provee la
> API completa de Jakarta EE — solo provee la parte de `Servlet/JSP`. El resto de especificaciones como `CDI`, `JPA`,
> etc. no las incluye.
>
> En la práctica esto funciona porque:
>
> - La especificación CDI (anotaciones como `@Inject`, `@ApplicationScoped`) queda incluida en el `.war` al compilar.
> - `Weld` (la implementación) es quien realmente las hace funcionar en runtime
>
> En un servidor completo como WildFly o Payara, el `scope=provided` sí tendría su significado completo — el servidor
> provee tanto la especificación como la implementación.

`weld-servlet-core` es la variante de Weld adaptada específicamente para
contenedores web simples como Tomcat. Al agregarlo dotamos a nuestro proyecto
de la **implementación** que necesita para que las anotaciones CDI funcionen
en runtime — la especificación ya la teníamos disponible desde `jakarta.jakartaee-api`.

> ✅ **Sobre la versión:** `weld-servlet-core 6.0.4.Final` es la versión correcta
> para tu stack — es compatible con **Jakarta EE 11** y **Java 25**. Las versiones
> anteriores (4.x) implementaban CDI 3.0 de Jakarta EE 9/10, mientras que Weld 6.x
> implementa **CDI 4.1** que es la especificación incluida en Jakarta EE 11.

## 🔧 Activando el Contexto CDI

### `beans.xml`

Para que `Weld` active el contenedor CDI en nuestra aplicación, necesitamos crear el archivo `beans.xml` en el
directorio `WEB-INF`. Sin este archivo, Weld no escanea ni registra ningún bean CDI — es el "interruptor" que activa
todo el sistema de inyección de dependencias.

```xml
<!-- src/main/webapp/WEB-INF/beans.xml -->
<!-- Solo necesitamos esta etiqueta para activar el contexto CDI -->
<beans/>
```

> 📌 El archivo puede estar vacío o contener solo `<beans/>`. En proyectos más avanzados se pueden configurar
> interceptores, decoradores y el modo de descubrimiento de beans, pero para nuestro caso es suficiente con activarlo.

## 🛒 Configurando el Carrito con `@SessionScoped`

El primer bean que transformamos a CDI es `ShoppingCart`. A continuación vemos los cambios en cadena que este refactor
provoca en el resto de la aplicación.

### `ShoppingCart`

Agregamos las anotaciones CDI para que el contenedor gestione su ciclo de vida:

```java

@Named           // nombre accesible desde EL: "shoppingCart" (clase con inicial en minúscula)
@SessionScoped   // una instancia por sesión de usuario
public class ShoppingCart implements Serializable { // Serializable obligatorio para @SessionScoped
    /* código sin cambios */
}
```

#### 🔍 Puntos clave

- **`@Named`** — registra el bean con el nombre `shoppingCart` (nombre de la clase con inicial en minúscula), haciéndolo
  accesible directamente desde las vistas JSP mediante EL: `${shoppingCart.items}`.
- **`@SessionScoped`** — garantiza que cada usuario tenga su **propia instancia** del carrito durante toda su sesión.
  Cuando la sesión expira o se invalida, CDI destruye la instancia automáticamente.
- **`implements Serializable`** — obligatorio para `@SessionScoped`. CDI necesita poder serializar el bean para
  gestionar su persistencia entre peticiones.

### `AppListener`

Sin CDI creábamos el `ShoppingCart` manualmente en `sessionCreated(...)`. Ahora que CDI gestiona su ciclo de vida con
`@SessionScoped`, esa línea ya no tiene sentido — CDI crea la instancia automáticamente cuando se necesita:

```java

@WebListener
public class AppListener implements ServletContextListener,
        ServletRequestListener, HttpSessionListener {

    /* otros métodos sin cambios */

    @Override
    public void sessionCreated(HttpSessionEvent se) {
        this.servletContext.log("Sesión HTTP inicializada!");
        // ✅ Ya no necesitamos instanciar ShoppingCart manualmente.
        // CDI lo gestiona automáticamente gracias a @SessionScoped
        // se.getSession().setAttribute("shopping-cart", new ShoppingCart());
    }
}
```

> 📌 Este es uno de los primeros beneficios visibles de CDI — eliminamos código de instanciación manual. El contenedor
> sabe cuándo crear, reutilizar y destruir el bean según su scope.

### `AddToCartServlet`

Antes obteníamos el carrito manualmente desde la sesión HTTP. Ahora CDI lo inyecta directamente como atributo de
instancia:

```java

@WebServlet("/carts/add")
public class AddToCartServlet extends HttpServlet {

    @Inject // CDI inyecta la instancia @SessionScoped del usuario actual
    private ShoppingCart shoppingCart;

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp)
            throws ServletException, IOException {
        /* código de obtención del producto sin cambios */

        if (optionalProduct.isPresent()) {
            CartItem cartItem = new CartItem(1, optionalProduct.get());

            // ✅ Usamos directamente el shoppingCart inyectado por CDI
            this.shoppingCart.addItemToCart(cartItem);

            // ❌ Ya no necesitamos esto:
            // HttpSession session = req.getSession();
            // ShoppingCart shoppingCart = (ShoppingCart) session.getAttribute("shopping-cart");
        }

        resp.sendRedirect(req.getContextPath() + "/carts/view");
    }
}
```

### `UpdateCartServlet`

El mismo patrón — inyectamos `ShoppingCart` con `@Inject` y eliminamos la obtención manual desde la sesión:

```java

@WebServlet("/carts/update")
public class UpdateCartServlet extends HttpServlet {

    @Inject
    private ShoppingCart shoppingCart;

    @Override
    protected void doPost(HttpServletRequest req, HttpServletResponse resp)
            throws ServletException, IOException {

        // ✅ Usamos directamente el shoppingCart inyectado por CDI
        this.updateProducts(req, this.shoppingCart);
        this.updateQuantities(req, this.shoppingCart);

        // ❌ Ya no necesitamos esto:
        // HttpSession session = req.getSession();
        // if (Objects.nonNull(session.getAttribute("shopping-cart"))) {
        //     ShoppingCart shoppingCart = (ShoppingCart) session.getAttribute("shopping-cart");

        resp.sendRedirect(req.getContextPath() + "/carts/view");
    }

    /* métodos updateProducts() y updateQuantities() sin cambios */
}
```

### Vistas JSP

Con `@Named` en `ShoppingCart`, CDI registra el bean con el nombre `shoppingCart` accesible directamente desde EL — sin
necesidad de `sessionScope['shopping-cart']`.

#### `header.jsp`

```html
<!-- ❌ Antes — acceso manual via sessionScope con notación de corchetes -->

<!-- ✅ Ahora — acceso directo por nombre CDI -->
<a class="nav-link"

</a>
```

#### `cart.jsp`


### 📊 Resumen del refactor — Carrito de compras

|                          | Sin CDI                                  | Con CDI                                     |
|--------------------------|------------------------------------------|---------------------------------------------|
| **Creación del carrito** | `new ShoppingCart()` en `AppListener`    | `@SessionScoped` — CDI lo gestiona          |
| **Acceso al carrito**    | `session.getAttribute("shopping-cart")`  | `@Inject ShoppingCart shoppingCart`         |
| **Acceso desde JSP**     | `${sessionScope['shopping-cart'].items}` | `${shoppingCart.items}`                     |
| **Ciclo de vida**        | Manual — el desarrollador lo controla    | Automático — CDI lo gestiona según el scope |

> 🔗 **Conexión con Quarkus:** En Quarkus este mismo patrón aplica exactamente igual — `@SessionScoped` + `@Named` +
> `@Inject`. La diferencia es que en Quarkus no necesitas `beans.xml` ni `weld-servlet-core` — el contenedor CDI (ArC)
> ya está integrado y configurado automáticamente. ✅

## 🔌 Registrando Conexión JDBC en el Contenedor CDI

### 📄 Configuración explícita del `beans.xml`

Anteriormente, usamos solo `<beans/>` para activar el contexto CDI. Ahora declaramos
el archivo de forma **explícita**, siguiendo la documentación oficial de Jakarta
[Declaring selected alternatives for a bean archive](https://jakarta.ee/specifications/cdi/4.1/jakarta-cdi-spec-4.1.html#declaring_selected_alternatives_bean_archive),
incluyendo el atributo `bean-discovery-mode`.

````xml
<!--Agregamos este archivo con esta etiqueta. Solo es para activar el contexto de dependencias-->
<beans xmlns="https://jakarta.ee/xml/ns/jakartaee"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       xsi:schemaLocation="https://jakarta.ee/xml/ns/jakartaee https://jakarta.ee/xml/ns/jakartaee/beans_3_0.xsd"
       version="3.0" bean-discovery-mode="all">
</beans>
````

> ⚠️ **Ojo:** esta declaración **no es equivalente** a un simple `<beans/>`. En nuestro
> stack (CDI 4.1), `<beans/>` equivale a `annotated`, mientras que aquí fijamos `all`
> explícitamente. Por eso conviene siempre declarar el modo y no depender del
> comportamiento por defecto.

#### 🔍 `bean-discovery-mode`

El atributo `bean-discovery-mode` controla **qué clases del proyecto son reconocidas y gestionadas** por el contenedor
CDI:

| Valor       | Comportamiento                                                                                                                                                                                                                |
|-------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `all`       | Todas las clases son candidatas a ser beans, incluso las que no tienen anotaciones. Las clases sin anotación de scope quedan como `@Dependent`                                                                                |
| `annotated` | Solo se reconocen las clases con una **anotación de definición de bean** (`@ApplicationScoped`, `@RequestScoped`, `@SessionScoped`, `@Dependent`, o un estereotipo que incluya alguna). Las clases sin ellas **no** son beans |
| `none`      | CDI ignora el archivo: es como no tenerlo. No se descubre ningún bean                                                                                                                                                         |

> 📌 Por ahora usamos `all` para que CDI gestione todas las clases del proyecto sin anotarlas una por una. Es la opción
> más cómoda durante el aprendizaje, pero más adelante pasaremos a `annotated`.

#### ⚠️ Importante: el valor por defecto depende de la versión de CDI

Cuando **no se declara** el atributo `bean-discovery-mode`, o el `beans.xml` está vacío (o es un simple `<beans/>`), el
comportamiento depende de la versión de CDI:

| Versión de CDI        | Jakarta EE        | `beans.xml` vacío o `<beans/>` |
|-----------------------|-------------------|--------------------------------|
| CDI 3.0 y anteriores  | EE 9 y anteriores | Se trata como **`all`**        |
| CDI 4.0 y posteriores | EE 10 y 11        | Se trata como **`annotated`**  |

#### 🤔 ¿Por qué nos confundimos al inicio?

El curso que seguimos está basado en **Jakarta EE 9 (CDI 3.0)**, donde un `<beans/>`
vacío activaba el modo `all`. Nuestro proyecto usa **Jakarta EE 11 (CDI 4.1)** con **Weld 6**, donde ese mismo
`<beans/>` activa `annotated`. Lo comprobamos en el log de arranque de Tomcat:

```bash
WELD-ENV-000014: Falling back to Java Reflection for bean-discovery-mode="annotated" discovery.
```

Ese mensaje apareció con un `<beans/>` vacío, lo que confirma que Weld lo trató como `annotated`.

#### ✅ Conclusión

Para evitar ambigüedades entre versiones, **declaramos siempre `bean-discovery-mode`
de forma explícita**. Por ahora usamos `all`, y más adelante trabajaremos con `annotated`,
que es el modo por defecto actual y el que usan los proyectos modernos.

> 🔗 **Conexión con Quarkus:** Quarkus **no usa `beans.xml`**: su descubrimiento de beans
> funciona siempre como `annotated`. Entender este modo ahora te prepara directamente para
> Quarkus. ✅

### 🏭 Registrando `Connection` como bean CDI — `ProducerResources`

En el proyecto sin CDI teníamos `DataSourceConnectionFactory` y `DriverManagerConnectionFactory` para obtener
conexiones. Con CDI podemos registrar la `Connection` directamente en el contenedor usando `@Produces`, eliminando esas
clases por completo.

`@Produces` convierte un método en una **fábrica de beans** — el objeto que retorna queda registrado en el contenedor
CDI y puede ser inyectado en cualquier otro bean:

````java
public class ProducerResources {

    private static final Logger log = Logger.getLogger(ProducerResources.class.getName());

    @Produces
    @RequestScoped
    @Named("connection")
    private Connection connection() throws NamingException, SQLException {
        log.info("Estableciendo conexión a la base de datos");
        // Paso 1 — accedemos al contexto raíz de JNDI
        Context initContext = new InitialContext();
        // Paso 2 — navegamos al subcontexto de recursos de la aplicación
        Context envContext = (Context) initContext.lookup("java:/comp/env");
        // Paso 3 — buscamos el DataSource por su nombre JNDI (definido en context.xml)
        DataSource ds = (DataSource) envContext.lookup("jdbc/MySQLResource");
        // Paso 4 — pedimos una conexión al pool
        return ds.getConnection();
    }
}
````

#### 🔍 Puntos clave

- `@Produces` — marca el método como productor de beans. CDI llama a este método cada vez que necesita una instancia
  de `Connection` para inyectar en algún bean que la requiera.
- `@RequestScoped` — la conexión vive exactamente una petición HTTP. Al finalizar la petición CDI la destruye
  automáticamente. Es el scope correcto para conexiones JDBC — cada petición debe tener su propia conexión.
- `@Named("connection")` — asigna un nombre explícito al bean para poder referenciarlo por nombre al inyectarlo.
  Útil cuando existen múltiples beans del mismo tipo.

> 📌 **Eliminación de clases innecesarias:** Con `ProducerResources` registrando la `Connection` en el contenedor CDI,
> las clases `DataSourceConnectionFactory` y `DriverManagerConnectionFactory` ya no son necesarias y pueden eliminarse
> del proyecto. CDI se encarga de todo.

### 🔗 Modificando `DatabaseConnectionFilter`

Antes obteníamos la conexión llamando manualmente a `DataSourceConnectionFactory.getConnection()`. Ahora que la
`Connection` está registrada en el contenedor CDI, simplemente la inyectamos:

````java

@WebFilter("/*") //El patrón definido indica que se aplicará a cualquier ruta
public class DatabaseConnectionFilter implements Filter {

    private static final Logger log = Logger.getLogger(DatabaseConnectionFilter.class.getName());

    @Inject
    @Named("connection") // inyecta el bean Connection producido por ProducerResources
    private Connection conn;

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {

        // ✅ Antes: try (Connection connection = DataSourceConnectionFactory.getConnection())
        // ✅ Ahora: la conexión ya viene inyectada por CDI
        try (Connection connection = this.conn) {

            // Desactivamos autoCommit para manejar la transacción manualmente
            if (connection.getAutoCommit()) {
                log.info("Desactivando autoCommit");
                connection.setAutoCommit(false);
            }

            try {
                // Compartimos la conexión con el servlet vía atributo del request
                log.info("Agregando 'connection' al request");
                request.setAttribute("connection", connection);

                chain.doFilter(request, response); // Continuamos con la cadena de filtros hasta llegar al Servlet

                log.info("Realizando 'commit' en la base de datos");
                connection.commit(); // tod OK → confirmamos cambios
            } catch (SQLException | DatabaseException ex) {
                log.warning("Realizando 'rollback' en la base de datos");
                connection.rollback(); // algo falló → revertimos cambios

                HttpServletResponse httpServletResponse = (HttpServletResponse) response;
                httpServletResponse.sendError(HttpServletResponse.SC_INTERNAL_SERVER_ERROR, ex.getMessage());
                ex.printStackTrace();
            }
        } catch (SQLException ex) {
            ex.printStackTrace(); // fallo al obtener la conexión
        }
    }
}
````

#### 🔍 Puntos clave

- `@Inject @Named("connection")` — inyecta la `Connection` registrada por `ProducerResources`. Usamos `@Named`
  explícitamente para dejar claro qué bean estamos inyectando, aunque solo exista uno de tipo `Connection`.
- `try (Connection connection = this.conn)` — seguimos usando `try-with-resources` para garantizar el cierre de la
  conexión. La diferencia es que ahora `this.conn` viene inyectada por CDI en lugar de obtenerse manualmente.

> ⚠️ **Nota — Inyección por campo vs constructor:** IntelliJ IDEA marca el `@Inject` en el campo con un warning:
> *"Remove this field injection and use constructor injection instead"*
>
> La **inyección por constructor** es la práctica recomendada porque:
> - Hace las dependencias explícitas y obligatorias.
> - Facilita las pruebas unitarias (puedes pasar mocks directamente).
> - Evita que el objeto exista en un estado incompleto.
>
> Sin embargo, CDI soporta perfectamente la inyección por campo con `@Inject` y para fines de aprendizaje la dejamos así
> porque es más visual y directa. En un proyecto productivo lo correcto sería usar inyección por constructor.

### 📊 Resumen del refactor — Conexión a base de datos

|                                      | Sin CDI                                                          | Con CDI                                                    |
|--------------------------------------|------------------------------------------------------------------|------------------------------------------------------------|
| **Obtención de conexión**            | `DataSourceConnectionFactory.getConnection()`                    | `@Inject @Named("connection") Connection conn`             |
| **Responsable de crear la conexión** | La clase la crea manualmente                                     | CDI llama a `ProducerResources.connection()`               |
| **Ciclo de vida**                    | Manual — `try-with-resources`                                    | `@RequestScoped` — CDI la destruye al finalizar el request |
| **Clases de fábrica**                | `DataSourceConnectionFactory` / `DriverManagerConnectionFactory` | Eliminadas — reemplazadas por `@Produces`                  |

## 🧩 Componentes CDI: DAOs, Servicios y Filtro

En esta sección transformamos los DAOs y servicios para que sean gestionados por CDI. El patrón es consistente en todos:
anotamos la clase con un scope y usamos `@Inject` para recibir sus dependencias en lugar de crearlas manualmente.

### `ProductDAOImpl`

Anotamos la clase con `@ApplicationScoped` — una sola instancia para toda la aplicación — e inyectamos la `Connection`
producida por `ProducerResources` mediante inyección por campo:

````java

@ApplicationScoped
public class ProductDAOImpl implements GenericDAO<Product> {

    private static final String SQL_ALL_PRODUCTS = """
            SELECT p.*, c.name AS category_name
            FROM products AS p
                INNER JOIN categories AS c ON(p.category_id = c.id)
            """;

    @Inject
    @Named("connection")
    private Connection connection; // CDI inyecta la Connection de @RequestScoped

    @Override
    public List<Product> getAll() throws SQLException {
        List<Product> products = new ArrayList<>();
        try (Statement statement = this.connection.createStatement();
             ResultSet resultSet = statement.executeQuery(SQL_ALL_PRODUCTS + " ORDER BY p.id ASC")) {
            while (resultSet.next()) {
                products.add(this.buildProduct(resultSet));
            }
        }
        return products;
    }

    /* otros métodos sin cambios */
}
````

### `CategoryDAOImpl`

Mismo scope `@ApplicationScoped`, pero aquí usamos **inyección por constructor** — la forma recomendada por CDI e
IntelliJ. El `@Inject` va en el constructor y `@Named` identifica qué bean inyectar:

````java

@ApplicationScoped
public class CategoryDAOImpl implements GenericDAO<Category> {

    private final Connection connection; // final → inmutable tras la construcción

    @Inject
    public CategoryDAOImpl(@Named("connection") Connection connection) {

    @Override
    public List<Category> getAll() throws SQLException {

        try (Statement statement = this.connection.createStatement();
             ResultSet resultSet = statement.executeQuery("SELECT * FROM categories")) {
            while (resultSet.next()) {
                categories.add(this.buildCategory(resultSet));
            }
        }

        return categories;
    }
    /* otros métodos sin cambios */
}
````

> 📌 **Inyección por campo vs constructor:** En `ProductDAOImpl` usamos inyección por campo (`@Inject` en el atributo)
> y en `CategoryDAOImpl` usamos inyección por constructor (`@Inject` en el constructor). Ambas son válidas en CDI. La
> inyección por constructor es la recomendada porque permite declarar el atributo como `final`, garantizando que la
> dependencia nunca sea `null` después de la construcción.

### `DatabaseConnectionFilter` — Eliminando la propagación de la conexión

Este es el cambio más importante de esta sección. En el proyecto sin CDI propagábamos la conexión manualmente mediante
`request.setAttribute("connection", connection)` para que los servlets pudieran accederla. Ahora que la `Connection`
está registrada en el contenedor CDI con `@RequestScoped`, **cualquier bean puede inyectarla directamente** — ya no
necesitamos propagarla por el request:

````java

@WebFilter("/*") //El patrón definido indica que se aplicará a cualquier ruta
public class DatabaseConnectionFilter implements Filter {

    private static final Logger log = Logger.getLogger(DatabaseConnectionFilter.class.getName());

    @Inject
    @Named("connection") // inyecta el bean Connection producido por ProducerResources
    private Connection conn;

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {

        // ✅ Antes: try (Connection connection = DataSourceConnectionFactory.getConnection())
        // ✅ Ahora: la conexión ya viene inyectada por CDI
        try (Connection connection = this.conn) {

            // Desactivamos autoCommit para manejar la transacción manualmente
            if (connection.getAutoCommit()) {
                log.info("Desactivando autoCommit");
                connection.setAutoCommit(false);
            }

            try {
                // ✅ Ya no necesitamos: request.setAttribute("connection", connection)
                // La conexión está disponible via @Inject en cualquier bean CDI
                chain.doFilter(request, response); // Continuamos con la cadena de filtros hasta llegar al Servlet

                log.info("Realizando 'commit' en la base de datos");
                connection.commit(); // tod OK → confirmamos cambios
            } catch (SQLException | DatabaseException ex) {
                log.warning("Realizando 'rollback' en la base de datos");
                connection.rollback(); // algo falló → revertimos cambios

                HttpServletResponse httpServletResponse = (HttpServletResponse) response;
                httpServletResponse.sendError(HttpServletResponse.SC_INTERNAL_SERVER_ERROR, ex.getMessage());
                ex.printStackTrace();
            }
        } catch (SQLException ex) {
            ex.printStackTrace(); // fallo al obtener la conexión
        }
    }
}
````

#### 🔍 ¿Por qué ya no necesitamos `request.setAttribute(...)`?

```
Sin CDI:
    Filter → request.setAttribute("connection", conn) → Servlet
    Servlet → (Connection) request.getAttribute("connection") → DAO → Service

Con CDI:
    Filter → [gestiona transacción]  → Servlet
    Servlet → @Inject Service        → @Inject DAO
    DAO     → @Inject Connection     ← misma instancia @RequestScoped
```

La clave está en el scope `@RequestScoped` de la `Connection` — CDI garantiza que todos los beans que inyecten
`Connection` dentro de la **misma petición HTTP** recibirán **la misma instancia**. El filtro, el servlet, el servicio
y el DAO comparten la misma conexión y, por tanto, la misma transacción, sin necesidad de pasarla manualmente.

### 📊 Resumen del refactor — DAOs y Servicios

|                            | Sin CDI                                        | Con CDI                                          |
|----------------------------|------------------------------------------------|--------------------------------------------------|
| **Creación de DAOs**       | `new ProductDAOImpl(connection)` en el Service | `@Inject` — CDI los inyecta                      |
| **Paso de conexión**       | Por constructor manualmente                    | `@Inject @Named("connection")`                   |
| **Propagación al servlet** | `request.setAttribute("connection", conn)`     | Eliminada — CDI la comparte por `@RequestScoped` |
| **Scope de DAOs/Services** | Sin gestión de ciclo de vida                   | `@ApplicationScoped` — una instancia por app     |

> 🔗 **Conexión con Quarkus:** En Quarkus este mismo patrón aplica exactamente igual. Los repositorios y servicios son
> `@ApplicationScoped` por defecto, la conexión a BD es gestionada automáticamente por Hibernate + Agroal, y
> `@Transactional` reemplaza todo el filtro de transacción. La inyección con `@Inject` es idéntica. ✅

Sin embargo, el contenedor CDI sí puede **inyectarles dependencias** mediante `@Inject`, lo que nos permite eliminar
toda la instanciación manual que teníamos antes.

### `ProductFormServlet`

Inyectamos `ProductService` y eliminamos la conexión manual. Además, mejoramos la validación del `productId` y
`categoryId` verificando también que no sean cadenas vacías con `isBlank()`:

````java

@WebServlet("/products/form")
public class ProductFormServlet extends HttpServlet {

    @Inject
    private ProductService productService;

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp)
            throws ServletException, IOException {
        // Si viene productId → edición, si no → creación
        Long productId = Objects.nonNull(req.getParameter("productId"))
                ? Long.parseLong(req.getParameter("productId"))
                : null;

        // Producto por defecto vacío para el formulario de creación
        Product product = new Product();
        product.setCategory(new Category());

        if (Objects.nonNull(productId)) {
            Optional<Product> optionalProduct = this.productService.getProduct(productId);
            if (optionalProduct.isPresent()) {
                product = optionalProduct.get();
            }
        }

        req.setAttribute("categories", this.productService.getAllCategories());
        req.setAttribute("product", product);
        req.setAttribute("title", req.getAttribute("title") + ": Listado de productos");

        this.getServletContext()
                .getRequestDispatcher("/form.jsp")
                .forward(req, resp);
    }

    @Override
    protected void doPost(HttpServletRequest req, HttpServletResponse resp)
            throws ServletException, IOException {
        // Lee los parámetros del formulario
        String name = req.getParameter("name");
        String sku = req.getParameter("sku");
        LocalDateTime createdAt = LocalDateTime.now();
        BigDecimal price = new BigDecimal(req.getParameter("price"));

        // ✅ isBlank() como segunda validación — cubre el caso de string vacío
        // cuando el formulario envía productId vacío en modo creación.
        // Si viene productId → UPDATE, si no → INSERT.
        Long productId = Objects.nonNull(req.getParameter("productId")) && !req.getParameter("productId").isBlank()
                ? Long.parseLong(req.getParameter("productId"))
                : null;
        Long categoryId = Objects.nonNull(req.getParameter("categoryId")) && !req.getParameter("categoryId").isBlank()
                ? Long.parseLong(req.getParameter("categoryId"))
                : null;

        // Construye el objeto Product con los datos del formulario
        Category category = new Category();
        category.setId(categoryId);

        Product product = new Product();
        product.setId(productId);
        product.setName(name);
        product.setCategory(category);
        product.setPrice(price);
        product.setSku(sku);
        product.setCreatedAt(createdAt);

        this.productService.saveProduct(product);
        resp.sendRedirect(req.getContextPath() + "/products");
    }
}
````

> 📌 **`isBlank()` como mejora:** En el proyecto sin CDI solo validábamos con `Objects.nonNull()`. Ahora agregamos
> `!req.getParameter("productId").isBlank()` porque el formulario de creación envía `productId` como string vacío `""`
> (no como `null`), lo que causaría un `NumberFormatException` al intentar convertirlo con `Long.parseLong("")`.

### 🏷️ Anotación `@Resource` — Inyectando el `DataSource` de Tomcat

Anteriormente en `ProducerResources` obteníamos el `DataSource` de forma **programática** mediante JNDI — navegando
manualmente por el contexto con `InitialContext` y `lookup()`. Ahora usamos la anotación `@Resource` que simplifica
enormemente este proceso:

```java
// ❌ Antes — obtención programática del DataSource (verbose)
@Produces
@RequestScoped
@Named("connection")
private Connection connection() throws NamingException, SQLException {
    log.info("Estableciendo conexión a la base de datos");
    Context initContext = new InitialContext();
    Context envContext = (Context) initContext.lookup("java:/comp/env");
    DataSource ds = (DataSource) envContext.lookup("jdbc/MySQLResource");
    return ds.getConnection();
}

// ✅ Ahora — inyección declarativa con @Resource (limpio y directo)
@Resource(name = "jdbc/MySQLResource")
private DataSource dataSource;
```

La clase `ProducerResources` queda así:

````java
public class ProducerResources {

    private static final Logger log = Logger.getLogger(ProducerResources.class.getName());

    // Inyecta directamente el DataSource registrado en Tomcat (context.xml)
    // por su nombre JNDI — sin necesidad de lookup manual
    @Resource(name = "jdbc/MySQLResource")
    private DataSource dataSource;

    @Produces
    @RequestScoped
    @Named("connection")
    private Connection connection() throws NamingException, SQLException {
        log.info("Estableciendo conexión a la base de datos");
        return this.dataSource.getConnection();
    }
}
````

#### 🔍 ¿Qué es `@Resource`?

`@Resource` es una anotación estándar de Jakarta EE que permite **inyectar recursos del servidor** directamente en un
bean, sin necesidad de código programático. El contenedor (Tomcat en nuestro caso) localiza el recurso por su nombre
JNDI y lo inyecta automáticamente.

| Aspecto              | `@Resource`                                  | JNDI programático               |
|----------------------|----------------------------------------------|---------------------------------|
| **Código necesario** | Una sola línea                               | 3-4 líneas de lookup            |
| **Legibilidad**      | Alta — declarativo                           | Baja — imperativo               |
| **Mantenimiento**    | El nombre en un solo lugar                   | El nombre repetido en el código |
| **Tipo de recursos** | DataSources, colas JMS, variables de entorno | Cualquier recurso JNDI          |

> 📌 **`name = "jdbc/MySQLResource"`** — debe coincidir exactamente con el atributo `name` definido en el `context.xml`
> de Tomcat. Es el mismo nombre JNDI que usábamos antes en el `lookup()`.

### 📊 Resumen del refactor — `LoginService` y `ProducerResources`

|                               | Sin CDI                                         | Con CDI                                       |
|-------------------------------|-------------------------------------------------|-----------------------------------------------|
| **`LoginServiceSessionImpl`** | `new LoginServiceSessionImpl()` en cada servlet | `@ApplicationScoped` + `@Inject LoginService` |
| **Obtención del DataSource**  | JNDI programático (3-4 líneas)                  | `@Resource(name="jdbc/MySQLResource")`        |
| **`ProducerResources`**       | Lógica de lookup en el método                   | Solo `dataSource.getConnection()`             |

> 🔗 **Conexión con Quarkus:** En Quarkus `@Resource` no se usa — el `DataSource` se configura en
> `application.properties` y se inyecta directamente con `@Inject DataSource dataSource`. El concepto es el mismo:
> inyección declarativa sin código programático. ✅

## 🎯 Calificadores Personalizados con `@Qualifier`

Como vimos en la teoría, `@Named` desambigua por un **nombre en texto** (un String propenso a typos), mientras que
`@Qualifier` permite crear **anotaciones personalizadas** para identificar implementaciones de forma más robusta y
segura.

En este proyecto solo tenemos una conexión a MySQL, pero en un escenario real podríamos tener múltiples conexiones —
PostgreSQL, Oracle, MongoDB, etc. Usar `@Named` para distinguirlas funcionaría, pero es frágil. La solución correcta es
un `@Qualifier` propio por cada tipo de conexión.

### Creando la anotación `@MySQLConnection`

````java

@Qualifier
@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.FIELD, ElementType.PARAMETER, ElementType.METHOD, ElementType.TYPE})
public @interface MySQLConnection {
}
````

#### 🔍 Meta-anotaciones explicadas

- **`@Qualifier`** — le indica a CDI que esta anotación será usada como identificador para distinguir entre múltiples
  beans del mismo tipo. Sin esta meta-anotación, CDI ignoraría nuestra anotación personalizada como qualifier.
- **`@Retention(RetentionPolicy.RUNTIME)`** — define que la anotación sobrevive hasta el tiempo de ejecución. CDI
  necesita leerla en runtime mediante reflexión para resolver las inyecciones. Sin esto, la anotación desaparecería al
  compilar y CDI no podría verla.
- **`@Target`** — define en qué lugares del código puede usarse nuestra anotación. Los valores configurados son:

| `ElementType` | Permite usar `@MySQLConnection` en... | Ejemplo                                            |
|---------------|---------------------------------------|----------------------------------------------------|
| `FIELD`       | Atributos de instancia                | `@MySQLConnection private Connection conn`         |
| `PARAMETER`   | Parámetros de método o constructor    | `(@MySQLConnection Connection conn)`               |
| `METHOD`      | Métodos — incluye métodos `@Produces` | `@MySQLConnection private Connection connection()` |
| `TYPE`        | Clases, interfaces o enums            | `@MySQLConnection public class MiClase`            |

### Aplicando `@MySQLConnection` en `ProducerResources`

Reemplazamos `@Named("connection")` por nuestro qualifier personalizado en el método productor. Como `METHOD` está
incluido en `@Target`, es válido anotarlo directamente en el método `@Produces`:

````java
public class ProducerResources {

    private static final Logger log = Logger.getLogger(ProducerResources.class.getName());

    @Resource(name = "jdbc/MySQLResource")
    private DataSource dataSource;

    @Produces
    @RequestScoped
    @MySQLConnection // ✅ reemplaza @Named("connection") — más robusto y sin riesgo de typos
    private Connection connection() throws NamingException, SQLException {
        log.info("Estableciendo conexión a la base de datos");
        return this.dataSource.getConnection();
    }
}
````

### Usando `@MySQLConnection` en los componentes

Ahora reemplazamos `@Named("connection")` por `@MySQLConnection` en todos los beans que inyectan la conexión:

#### `DatabaseConnectionFilter`

````java

@WebFilter("/*")
public class DatabaseConnectionFilter implements Filter {

    private static final Logger log = Logger.getLogger(DatabaseConnectionFilter.class.getName());

    @Inject
    @MySQLConnection // ✅ antes: @Named("connection")
    private Connection conn;

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        /* codes */
    }
}
````

#### `ProductDAOImpl`

````java

@ApplicationScoped
public class ProductDAOImpl implements GenericDAO<Product> {

    @Inject
    @MySQLConnection // ✅ antes: @Named("connection")
    private Connection connection;

    /* codes */
}
````

#### `UserDAOImpl`

```java

@ApplicationScoped
public class UserDAOImpl implements UserDAO {

    @Inject
    @MySQLConnection  // ✅ antes: @Named("connection")
    private Connection connection;

    /* código sin cambios */
}
```

#### `CategoryDAOImpl`

```java

@ApplicationScoped
public class CategoryDAOImpl implements GenericDAO<Category> {

    private final Connection connection;

    @Inject
    public CategoryDAOImpl(@MySQLConnection Connection connection) { // ✅ ElementType.PARAMETER en acción
        this.connection = connection;
    }

    /* código sin cambios */
}
```

> 📌 `CategoryDAOImpl` es el único que usa inyección por constructor — aquí `@MySQLConnection` va en el **parámetro**
> del constructor, no en el campo. Por eso incluimos `ElementType.PARAMETER` en el `@Target` de la anotación.

### 📊 Resumen del refactor — `@Named` vs `@Qualifier`

| Aspecto             | `@Named("connection")`          | `@Qualifier` (`@MySQLConnection`)                     |
|---------------------|---------------------------------|-------------------------------------------------------|
| **Tipo**            | Anotación estándar CDI          | Anotación estándar CDI + implementación personalizada |
| **Identificación**  | Por String `"connection"`       | Por anotación propia (`@MySQLConnection`)             |
| **Riesgo de typos** | ⚠️ Alto — falla en runtime      | ✅ Nulo — falla en compilación                        |
| **Refactoring**     | ⚠️ Manual — buscar el String    | ✅ Automático con el IDE                              |
| **Escalabilidad**   | Difícil — más Strings similares | Fácil — una anotación por tipo de conexión            |
| **Legibilidad**     | Regular                         | Alta — el nombre dice exactamente qué es              |

> 🔗 **Conexión con Quarkus:** En Quarkus `@Qualifier` funciona exactamente igual. Es la forma recomendada para
> distinguir múltiples implementaciones de una misma interfaz. De hecho, Quarkus lo usa internamente — por ejemplo
> `@RestClient` es un qualifier que identifica beans generados para clientes REST. ✅

## 🏷️ Estereotipos CDI con `@Stereotype`

Un **estereotipo** (`@Stereotype`) es una meta-anotación de CDI que permite **agrupar varias anotaciones en una sola**.
Su propósito es reducir la repetición cuando un mismo conjunto de anotaciones se aplica consistentemente a múltiples
clases.

En lugar de anotar cada clase con `@Named`, `@SessionScoped`, etc., defines un estereotipo que los agrupa y aplicas solo
ese estereotipo.

### ¿Cuándo usar `@Stereotype`?

- Cuando varias clases comparten exactamente el mismo conjunto de anotaciones CDI.
- Para estandarizar la configuración de beans en proyectos grandes.
- Para crear "plantillas" de comportamiento reutilizables y con nombres semánticos.
- Para reducir el riesgo de olvidar alguna anotación al crear nuevas clases.

### Creando el estereotipo `@ShoppingCartSessionBean`

```java

@Stereotype                          // marca esta anotación como un estereotipo CDI
@Named                               // el bean será accesible desde EL por su nombre
@SessionScoped                       // una instancia por sesión de usuario
@Retention(RetentionPolicy.RUNTIME)  // visible en runtime para que CDI pueda leerlo
@Target(ElementType.TYPE)            // solo aplicable a clases
public @interface ShoppingCartSessionBean {
}
```

#### 🔍 Meta-anotaciones explicadas

- **`@Stereotype`** — le indica a CDI que esta anotación es un estereotipo. CDI procesará todas las anotaciones que
  contiene (`@Named`, `@SessionScoped`) como si estuvieran directamente en la clase que lo use.
- **`@Named`** — incluido en el estereotipo para que cualquier clase anotada con `@ShoppingCartSessionBean` sea
  accesible desde EL con su nombre en camelCase.
- **`@SessionScoped`** — define el scope de todas las clases que usen este estereotipo. Al estar aquí, ya no necesitamos
  repetirlo en cada clase.
- **`@Retention(RetentionPolicy.RUNTIME)`** — obligatorio para que CDI pueda leer el estereotipo en tiempo de ejecución
  mediante reflexión.
- **`@Target(ElementType.TYPE)`** — restringe el uso del estereotipo solo a
  clases. A diferencia de `@MySQLConnection` que podía usarse en campos, parámetros y métodos, un estereotipo
  típicamente solo aplica a tipos.

### Aplicando `@ShoppingCartSessionBean`

```java
// ❌ Antes — anotaciones repetidas explícitamente
@Named
@SessionScoped
public class ShoppingCart implements Serializable {
    /* código sin cambios */
}

// ✅ Ahora — un solo estereotipo reemplaza todas las anotaciones
@ShoppingCartSessionBean
public class ShoppingCart implements Serializable {
    /* código sin cambios */
}
```

El resultado es exactamente el mismo — `ShoppingCart` sigue siendo un bean `@SessionScoped` accesible desde `EL` como
`${shoppingCart}`. La diferencia es que ahora esa configuración vive en un solo lugar: **el estereotipo.**

> 📌 **Analogía con Spring:** En Spring Boot existe `@Service`, `@Repository` y `@Controller` — todos son estereotipos
> que agrupan `@Component` con semántica adicional. `@Stereotype` de CDI es exactamente el mismo concepto, pero te
> permite **crear los tuyos propios** con cualquier combinación de anotaciones CDI.

> 🔗 **Conexión con Quarkus:** Quarkus soporta `@Stereotype` de CDI exactamente igual. Es una herramienta muy útil en
> proyectos Quarkus grandes donde muchos beans comparten el mismo scope y configuración. ✅

## 🔍 Bean Discovery Mode `annotated` y anotación `@Disposes`

En esta lección vemos dos temas:

- 🔎 **`bean-discovery-mode="annotated"`**: cómo controlar qué clases descubre CDI.
- 🧹 **`@Disposes`**: cómo cerrar recursos automáticamente cuando termina el ciclo de vida de un bean.

### 🔎 Bean Discovery Mode: `annotated`

En el `beans.xml` cambiamos `bean-discovery-mode` de `all` a `annotated`:

````xml
<!--Agregamos este archivo con esta etiqueta. Solo es para activar el contexto de dependencias-->
<beans xmlns="https://jakarta.ee/xml/ns/jakartaee"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       xsi:schemaLocation="https://jakarta.ee/xml/ns/jakartaee https://jakarta.ee/xml/ns/jakartaee/beans_3_0.xsd"
       version="3.0" bean-discovery-mode="annotated">
</beans>
````

#### 📊 `all` vs `annotated`

|                               | `all`                                                                     | `annotated`                                                 |
|-------------------------------|---------------------------------------------------------------------------|-------------------------------------------------------------|
| **¿Qué clases descubre CDI?** | Todas las del proyecto                                                    | Solo las que tienen una **anotación de definición de bean** |
| **Clases sin anotación**      | Se registran como beans `@Dependent`                                      | Se ignoran: no son beans                                    |
| **Riesgo**                    | Registra clases que no deberían ser beans (modelos, DTOs, excepciones...) | Si olvidas anotar una clase, CDI no la verá                 |
| **Rendimiento de arranque**   | Escanea todo                                                              | Más ligero                                                  |

#### 🏷️ ¿Qué es una "anotación de definición de bean"?

Es una anotación que le dice a CDI: *"esta clase es un bean, regístrala"*. Las más comunes son:

- Los scopes: `@ApplicationScoped`, `@SessionScoped`, `@RequestScoped`, `@ConversationScoped` y `@Dependent`.
- Los estereotipos (`@Stereotype`) que incluyan alguno de esos scopes, como nuestro `@ShoppingCartSessionBean`.

> ⚠️ Anotaciones como `@Named`, `@Inject`, `@Produces` o un `@Qualifier` **no** definen un bean por sí solas.

#### ❌ El problema: `ProducerResources` sin anotación

Con `annotated`, nuestra clase `ProducerResources` deja de ser descubierta, porque no tiene ninguna anotación de
definición de bean. Tener un método `@Produces` dentro **no es suficiente**:

````java
// ❌ Con bean-discovery-mode="annotated" esta clase es IGNORADA por CDI
public class ProducerResources {

    private static final Logger log = Logger.getLogger(ProducerResources.class.getName());

    @Resource(name = "jdbc/MySQLResource")
    private DataSource dataSource;

    @Produces
    @RequestScoped
    @MySQLConnection
    private Connection connection() throws NamingException, SQLException {
        log.info("Estableciendo conexión a la base de datos");
        return this.dataSource.getConnection();
    }
}
````

Consecuencias:

- El método `@Produces` no se registra, así que **no existe ningún bean `Connection`**.
- El `@Resource` no se inyecta, porque la clase no es gestionada por CDI.
- Al desplegar, `Weld` falla con un error de **dependencias no satisfechas** (*Unsatisfied dependencies for type
  Connection with qualifiers @MySQLConnection*) en los beans que intentan inyectar la conexión.

#### ✅ La solución: anotar la clase con un scope

````java

@ApplicationScoped // ✅ anotación de definición de bean: ahora CDI sí la descubre
public class ProducerResources {

    private static final Logger log = Logger.getLogger(ProducerResources.class.getName());

    @Resource(name = "jdbc/MySQLResource")
    private DataSource dataSource;

    @Produces
    @RequestScoped
    @MySQLConnection
    private Connection connection() throws NamingException, SQLException {
        log.info("Estableciendo conexión a la base de datos");
        return this.dataSource.getConnection();
    }
}
````

> 📌 Usamos `@ApplicationScoped` porque basta **una sola instancia** de esta clase fábrica para toda la aplicación. Lo
> que se crea por petición es la `Connection` que produce (`@RequestScoped`).

#### 🧩 ¿Cómo afecta `annotated` al resto del proyecto?

| Clase                                               | ¿Es descubierta?      | Motivo                                                                               |
|-----------------------------------------------------|-----------------------|--------------------------------------------------------------------------------------|
| DAOs y Services                                     | ✅ Sí                 | Tienen `@ApplicationScoped`                                                          |
| `LoginServiceSessionImpl`                           | ✅ Sí                 | Tiene `@ApplicationScoped`                                                           |
| `ShoppingCart`                                      | ✅ Sí                 | Su estereotipo incluye `@SessionScoped`                                              |
| `ProducerResources`                                 | ✅ Sí (tras anotarla) | Ahora tiene `@ApplicationScoped`                                                     |
| Modelos (`Product`, `User`, `Category`, `CartItem`) | ❌ No                 | No son beans, y es lo deseable                                                       |
| Servlets, Filters y Listeners                       | ➖ No aplica          | Los gestiona el contenedor web. `Weld` les inyecta dependencias sin importar el modo |

> 💡 **Ventaja de `annotated`:** con `all`, cada clase del proyecto, incluidos los modelos, se registraba como bean
> `@Dependent` sin necesidad. Con `annotated` solo se registra lo que explícitamente marcamos.

> ⚡ **Rendimiento:** en modo `annotated`, `Weld` escanea por reflexión y lo avisa en el log de arranque
> (`WELD-ENV-000014`). Se puede acelerar el arranque agregando `io.smallrye:jandex` al classpath.

> ⚠️ **Recuerda:** a partir de CDI 4.0, un `beans.xml` vacío o con solo `<beans/>` se trata como `annotated`
> (antes era `all`). Aun así, declaramos `bean-discovery-mode="annotated"` de forma explícita para no depender del
> comportamiento por defecto de cada versión. Más detalle en la sección *"Registrando Conexión JDBC en el
> Contenedor CDI"*.

### 🧹 `@Disposes`: cerrando recursos automáticamente

Hasta ahora el `DatabaseConnectionFilter` abría y cerraba la conexión con `try-with-resources`. Con CDI podemos delegar
el **cierre** al mismo lugar donde se **crea**: la clase productora.

`@Disposes` marca un parámetro de un método como **destructor** del bean producido. Cuando el contexto del bean termina,
CDI invoca ese método automáticamente para liberar el recurso.

````java

@ApplicationScoped
public class ProducerResources {

    private static final Logger log = Logger.getLogger(ProducerResources.class.getName());

    @Resource(name = "jdbc/MySQLResource")
    private DataSource dataSource;

    // 🏭 Crea el recurso
    @Produces
    @RequestScoped
    @MySQLConnection
    private Connection connection() throws NamingException, SQLException {
        log.info("Estableciendo conexión a la base de datos");
        return this.dataSource.getConnection();
    }

    // 🧹 Destruye el recurso: CDI lo invoca al terminar el @RequestScoped
    public void close(@Disposes @MySQLConnection Connection connection) throws SQLException {
        connection.close();
        log.info("Cerrando conexión a la base de datos MySQL");
    }
}
````

#### 🔍 Puntos clave

- **`@Disposes`** va en el **parámetro** del método destructor. Ese parámetro es el objeto que CDI entrega para liberar.
- **Mismo qualifier**: el parámetro lleva `@MySQLConnection`, el mismo qualifier del productor, para que CDI sepa a qué
  `@Produces` corresponde.
- **Misma clase**: el método `@Disposes` debe estar en la **misma clase** que el `@Produces` que destruye.
- **Ejecución automática**: no hay que invocarlo. Como la `Connection` es `@RequestScoped`, CDI lo ejecuta al
  **finalizar cada petición HTTP**.

#### 🔄 Ciclo de vida de la conexión

```
HTTP Request
     │
     ▼
Primera inyección de Connection ──► @Produces connection()  → abre conexión (pool)
     │
     ▼
[Filter] setAutoCommit(false) → chain.doFilter() → commit / rollback
     │
     ▼
Fin del request (se destruye el contexto @RequestScoped)
     │
     ▼
@Disposes close(connection)  → cierra la conexión (la devuelve al pool)
```

> 📌 El `commit`/`rollback` ocurre en el filtro **antes** del cierre, porque el contexto `@RequestScoped` se destruye
> cuando la petición ya terminó.

#### ✂️ Impacto en `DatabaseConnectionFilter`

Como el cierre ya lo hace `@Disposes`, el filtro **deja de usar `try-with-resources`** y solo gestiona la transacción.
Ejemplo de cómo quedaría:

````java

@WebFilter("/*") //El patrón definido indica que se aplicará a cualquier ruta
public class DatabaseConnectionFilter implements Filter {

    private static final Logger log = Logger.getLogger(DatabaseConnectionFilter.class.getName());

    @Inject
    @MySQLConnection
    private Connection connection;

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {

        // El filtro solo quedaría para el manejo de las transacciones. Para cerrar la conexión lo haríamos
        // en la clase ProducerResources con la anotación @Disposes
        try {
            // Desactivamos autoCommit para manejar la transacción manualmente
            if (this.connection.getAutoCommit()) {
                log.info("Desactivando autoCommit");
                this.connection.setAutoCommit(false);
            }

            chain.doFilter(request, response);

            log.info("Realizando 'commit' en la base de datos");
            this.connection.commit(); // tod OK → confirmamos cambios

        } catch (SQLException | DatabaseException ex) {
            log.warning("Realizando 'rollback' en la base de datos");
            try {
                this.connection.rollback(); // algo falló → revertimos cambios
            } catch (SQLException rollbackEx) {
                ex.addSuppressed(rollbackEx); // ✅ "ex" sigue siendo la causa principal, y rollbackEx queda adjunta
            }

            HttpServletResponse httpServletResponse = (HttpServletResponse) response;
            httpServletResponse.sendError(HttpServletResponse.SC_INTERNAL_SERVER_ERROR, ex.getMessage());
            ex.printStackTrace();
        }
    }
}
````

`addSuppressed(...)` es un método de `Throwable` (desde Java 7) que adjunta una excepción secundaria a una excepción
principal, sin perderla.

#### 🤔 ¿Por qué lo usamos aquí?

Dentro del `catch` ya tenemos una excepción principal (`ex`), la que causó el fallo. Pero `connection.rollback()`
también puede lanzar su propia `SQLException`. Sin `addSuppressed(...)` tendríamos dos malas opciones:

- **Ignorar el error del rollback:** se pierde información valiosa.
- **Dejar que se propague:** el error del rollback *reemplazaría* a la excepción original, y perderíamos la causa real
  del fallo.

Con `addSuppressed(...)` se conserva ambas.

#### 🔍 Cómo se ve en el stack trace

Cuando haces `ex.printStackTrace()`, Java imprime la excepción principal y, debajo, las suprimidas:

````bash
java.sql.SQLException: Error al guardar el producto      ← causa principal
    at ...
    Suppressed: java.sql.SQLException: Connection is closed   ← fallo del rollback
        at ...
````

> 📌 Es el mismo mecanismo que usa `try-with-resources` internamente: si falla el cuerpo del `try` y además falla el
> `close()`, la excepción del `close()` se adjunta como suppressed a la principal.

> ⚠️ Si mantuvieras el `try-with-resources`, la conexión se cerraría **dos veces** (en el filtro y en `@Disposes`). No
> rompe nada porque `close()` es idempotente, pero es redundante y confunde quién es el responsable del cierre.

### 📊 Resumen de la lección

| Concepto                          | Qué hace                                                              | Cuándo usarlo                                                       |
|-----------------------------------|-----------------------------------------------------------------------|---------------------------------------------------------------------|
| `bean-discovery-mode="annotated"` | CDI solo descubre clases con anotación de definición de bean          | Para evitar registrar clases innecesarias y tener control explícito |
| Anotar `ProducerResources`        | Hace que CDI descubra la clase que contiene `@Produces` y `@Resource` | Siempre que uses `annotated`                                        |
| `@Disposes`                       | Libera automáticamente un recurso producido con `@Produces`           | Conexiones, clientes, streams y cualquier recurso que deba cerrarse |

> 🔗 **Conexión con Quarkus:** Quarkus **no usa `beans.xml`** y su descubrimiento funciona como `annotated`. Una
> diferencia: Quarkus (ArC) también descubre los métodos `@Produces` y `@Disposes` aunque su clase no tenga anotación de
> scope. `@Disposes` funciona igual. En la práctica, con `Hibernate + Agroal`, Quarkus gestiona y cierra las conexiones
> por ti. ✅
